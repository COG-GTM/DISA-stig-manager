# Cryptographic inventory and PQC readiness assessment

This directory holds the CDRL A009 deliverable for STIG Manager: a machine-generated cryptographic inventory and a narrative post-quantum cryptography (PQC) readiness assessment.

Nothing here changes application behavior. The scanner reads the repository; it does not modify it.

## Regenerate

From the repository root:

```bash
python3 scripts/crypto_inventory.py --out docs/security/crypto-inventory/
```

Useful options:

| Option | Effect |
|---|---|
| `--lts-resolves-to "24.x.y, OpenSSL 3.5.z"` | Record what `node:lts-alpine` / `lts/*` resolved to when you ran the scan. The scanner cannot know this by itself. |
| `--no-probe` | Do not run the local `node` binary to report its OpenSSL version and ML-KEM/ML-DSA availability. |
| `--dn-values` | Record full certificate subject/issuer values. By default only attribute types and self-signed status are recorded. |
| `--repo PATH` | Scan a different checkout. |
| `--no-xlsx` | Write JSON and the report only. |

## Prerequisites

- Python 3.10 or later (standard library only for scanning).
- `openpyxl` for the workbook: `pip install openpyxl`.
- Optional: `cryptography` (`pip install cryptography`) or the `openssl` command-line tool for certificate parsing. If neither is present, certificate entries are recorded as unparsed.
- Optional: `node` on `PATH` for the local runtime probe.
- Optional, for a PDF: `pandoc` or LibreOffice. Example: `pandoc PQC-Readiness-Assessment.md -o PQC-Readiness-Assessment.pdf`, or convert the Markdown to DOCX/HTML and run `soffice --headless --convert-to pdf`. The scanner does not produce the PDF; re-render it after regenerating the Markdown.

## Artifacts

| File | What it is |
|---|---|
| `crypto-inventory.json` | Full machine-readable output: inventory rows, libraries, certificates, dependencies, agility gaps, migration candidates, runtime pins, summary counts, method notes. Source of truth for the other two files. |
| `Cryptographic-Inventory.xlsx` | Workbook with sheets `Inventory` (Excel table, frozen header, autofilter, fill by quantum-vulnerability class), `Libraries`, `TLS-and-Certificates`, `Dependencies`, `Crypto-Agility-Gaps`, `Migration-Candidates`, `Summary`, `Method`. |
| `PQC-Readiness-Assessment.md` | Narrative report. Rendered from `PQC-Readiness-Assessment.template.md`; every count and table is filled from the JSON at render time. Edit the template, not the rendered file. |
| `PQC-Readiness-Assessment.template.md` | Report template. `{{PLACEHOLDER}}` tokens are replaced by the scanner. Rendering fails if a placeholder has no value. |
| `PQC-Readiness-Assessment.pdf` | Rendered copy of `PQC-Readiness-Assessment.md` (DOCX via the contractor's report template, exported with LibreOffice). A snapshot of the Markdown at the commit recorded in the JSON `summary`; not regenerated by the scanner. |

## What the scanner detects

Asymmetric algorithms (RSA, ECDSA, ECDH, Ed25519, DH) and key sizes where inferable; symmetric algorithms and modes; hash functions and whether each use is security-relevant; TLS configuration (protocol versions, cipher strings, certificate and key paths, `rejectUnauthorized`, HSTS, MySQL TLS); JWT/JWS/JWKS handling (accepted `alg` values, issuer/audience checks, JWKS caching); certificate and key material (PEM/CRT/KEY/JKS/P12 files, embedded PEM, JWKS `x5c`, TUF root metadata); cryptographic libraries and resolved versions from lockfiles; Node.js runtime pins in Dockerfiles, CI and packaging config; and hardcoded credential-shaped values.

Every inventory row carries asset ID, file and line, scope, category, algorithm, key size/curve, mode, purpose, library, protocol context, security relevance, quantum-vulnerability class, CNSA 2.0 target algorithm, crypto-agility rating, external dependency, migration priority with rationale, recommended action, roadmap phase and a redacted evidence string.

## Secrets are redacted

Secret rows record path, line and type only (for example `Database password literal (MYSQL_ROOT_PASSWORD)` or `JWT literal`). Matched values are never written to the JSON, the workbook or the report. Certificate subject and issuer values are withheld unless `--dn-values` is passed.

## Limits

The scanner is static and heuristic. It reports what the repository configures and flags what it does not configure; it does not observe TLS handshakes or token exchanges. Algorithms chosen at deployment time (identity provider signing key, TLS certificates, MySQL server policy, reverse proxy policy, the concrete Node/OpenSSL version behind a mutable image tag) are outside its view and must be recorded separately. The `Method` sheet and the Methodology section of the report list the exclusions and known limits in full.
